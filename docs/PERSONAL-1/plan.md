## 1. Архитектурын хил

`spec.md §1`-ийн гурван гадаргуу хэвээр. §8-ын өргөтгөлөөр **домэйн ба контентын байршил
өөрчлөгдсөн** (§9 өөрчлөлтийн бүртгэл):

```
repo/
├─ shared/        # Домэйн цөм. Хамаарал ТЭГ. Хоёр гадаргуу импортлоно.
│  ├─ types/      #   contracts.yaml-ийн TS төрөл
│  ├─ validate/   #   runtime validator (нэг хувилбар)
│  ├─ core/       #   тоглоомын БҮХ дүрэм — цэвэр функц
│  └─ content/    #   JSON контент пакет
├─ web-app/       # Vite + TS + Vitest. UI + services + app. Дүрэм ЭНД БАЙХГҮЙ.
│  └─ src/{app,ui,services}/ + tests/
└─ server/        # Node + TS + Vitest. HTTP + SQLite + домэйныг эрх бүхий талаар ажиллуулна.
```

**Хамаарлын чиглэл (зөрчих нь архитектур эвдэх):**

```
web-app/ui/  →  web-app/services/  →  shared/core/  →  shared/{types,validate}
server/src/  →  shared/core/       →  shared/{types,validate}
shared/content/ (зөвхөн өгөгдөл)   →  shared/types
```

- `web-app/src/ui/**` дотроос `shared/core/**` руу шууд импорт — хориотой (`AC UI-3`, машинаар шалгагдана).
- `server/` нь `web-app/`-аас ХЭЗЭЭ Ч импортлохгүй. Эсрэгээр ч үгүй.
- Домэйн функц бүр цэвэр: `(state, input) → { state, events[] }` (`spec.md D-2`).
- `shared/types` нь `contracts.yaml`-ийн цорын ганц TypeScript төлөөлөл. Контракт өөрчлөгдвөл
  ЭХЛЭЭД `contracts.yaml`, ДАРАА нь `shared/` (AGENT_ORCHESTRATION дүрэм 4).

⚠ **Яагаад домэйн `shared/`-д, `web-app/src/core/`-д биш:** сервер нь `BE-11`-ээр үйлдлийг
эрх бүхий талаар хэрэгжүүлэх тул ижил дүрэм хэрэгтэй. Дүрмийг хоёр газар бичих нь хоёр үнэн
үүсгэнэ — энэ бол `P-2`-ийн зарчмын шууд үргэлжлэл. Контент мөн адил: сервер `staminaCost`,
`xp`-г мэдэхгүйгээр үйлдэл шалгаж чадахгүй.

| BE-15 | Сервер асахдаа `shared/content/*.json`-ыг `shared/validate`-ээр шалгана. Хүчинтэй → `GET /api/health` 200 `{status:"ok", version, contentVersion}`. Хүчингүй → пакет тараахгүй, health **503** `{status:"degraded", reason}`. | [I] |
| BE-16 | Бүх 4xx/5xx хариу `application/problem+json` (`type`·`title`·`status`·`detail`·`code`). Лог нь бүтэцлэгдсэн JSON бөгөөд **PII агуулахгүй**: IP, `Authorization` толгой, token, save-ийн агуулга лог руу ОРОХГҮЙ (лог тест + сканнердсан тест). SIGTERM-д graceful shutdown. DB схем дугаарласан migration-аар үүснэ (гараар `CREATE TABLE` биш). | [I] |
| BE-17 | Токен тутам 60 хүсэлт/мин давбал **429** + `Retry-After`. Токенгүй `POST /api/players` нь глобал 30/мин (IP хадгалахгүй тул IP-д тулгуурлахгүй). Хязгаар процессын санах ойд (`P-11`). | [I] |

### 8.2 Яагаад энэ өргөтгөл — ба түүний үнэ

Ганц хэрэглэгчийн, бүртгэлгүй тоглоомд эрх бүхий сервер нь **хууран мэхлэлтээс хамгаалах**
зорилготой БИШ — тийм шаардлага байхгүй. Бодит ашиг нь хоёр:

1. **Нэг дүрэм** (`BE-10`): домэйн `shared/`-д шилжсэнээр сервер ба клиент ижил кодоор тооцоолно.
2. **Итгэмжтэй эвлэрүүлэг** (`BE-11…BE-13`): төхөөрөмж хооронд шилжихэд (`BE-14`) төлөв серверт
   баталгаажиж, snapshot-оор буцаах боломжтой.

**Үнэ:** офлайн ажиллагаа (`AC BE-7`) шаардлагатай хэвээр тул домэйн клиент дээр ч ажиллана —
хоёр талд ажиллуулах нь `T-49`-ийн эвлэрүүлэгийн нарийн төвөгтэй байдлыг нэмнэ. Энэ нь
ухамсартай солилцоо, `P-9`-ээр хязгаарлагдсан.

### 8.3 Өргөтгөлийг хасах зам

Хэрэв хянагчийн санал зөвхөн "backend нь энэ репод байг" гэсэн утгатай байсан бол
`T-42`, `T-44`, `T-45`, `T-46`, `T-49`, `T-50`-ыг хасаад `T-43`, `T-47`, `T-48`-ыг үлдээнэ
(эдгээр нь өргөтгөлгүй ч зөв: нэг дүрэм, контентын validation, ops хаалга). `T-01…T-41` огт
хөндөгдөхгүй. Өөр ямар ч task-д гинжин нөлөө үүсэхгүй.
